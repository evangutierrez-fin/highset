# Spec: context compiler, packs, sync targets, mentions (`highset-context`)

Requirements: CTX-5, CTX-7…10, CTX-13, HRN-2. ADRs: 0009, 0018, 0020, 0021.

Context quality is the owner's top priority (Q13.7). This module is the heart of HighSet.

## 1. Context packs (CTX-5)

A pack is a folder containing `pack.toml` and, optionally, its own files.

```toml
# content/packs/rust-backend/pack.toml
name = "rust-backend"
description = "Conventions and references for Rust backend services"
version = "1"

[include]
knowledge = ["kb:rust-error-handling", "kb:api-guidelines", "files/*.md"]   # slugs or paths relative to the pack
instructions = ["rust.instructions.md"]
skills = ["skills/cargo-expert"]
prompts = ["review.prompt.md"]
profiles = []
mcp_servers = ["github"]          # names from the MCP registry

[defaults]
inline = ["kb:rust-error-handling"]   # attach inline at task start; everything else goes on demand
agents = []                           # restrict the pack to these agents (empty = all)
```

- **Activation:**
  - project (`[context] packs = [...]` in `project.toml`);
  - task (`packs:` in the task frontmatter);
  - profile (`packs:` in a profile);
  - workspace or global config.
- **Composition:** the union of all active packs. Duplicates are removed. Conflicts (the same MCP server name with different commands, or the same skill name from different sources) are errors with an explanation. You resolve them by disabling one pack or overriding at a more specific level.
- **Starter packs** ship with v0.1: `software-core`, `research`, `data-analysis`, `automation` (Q1.6). Their content is short, practical and editable, and they can be copied into `content/packs/` with `highset pack new --from <starter>`.

## 2. Compilation

`compile(target: { project, task?, profile, agent }) -> ContextBundle` (type in `core-domain.md` §5).

**Pipeline:**

1. **Resolve configuration:** merge the layers global → workspace → project → task (`core-domain.md` §6).
2. **Resolve the profile:** `harness.md` §3 (layered, with provenance).
3. **Collect sources:**
   - convention files from every level (`knowledge.md` §4);
   - active packs;
   - the task (title, body, acceptance criteria) and its spec/plan/tasks files from the worktree;
   - approved memory;
   - the MCP registry entries the profile or packs enable.
4. **Filter:** apply levels (shadowing) and audience for `{agent, profile, task}`. Excluded items are recorded in provenance with the reason ("audience: agents=[codex]").
5. **Classify:**
   - **always-on:** `PROJECT.md`, `*.instructions.md`, profile instructions, `MEMORY.md`, the task brief;
   - **attachments:** the spec, plan and tasks of the current phase, pack `inline` items, mentions;
   - **on-demand:** everything else visible.
6. **Budget.** Estimate tokens as `ceil(chars / 4)`; this is configurable, and an exact tokenizer is not required. Defaults:

   | Section | Default budget |
   |---|---|
   | Always-on instructions | 8,000 tokens |
   | Attachments | 24,000 tokens |
   | On-demand index | 2,000 tokens (titles + ids) |

   Overflow is moved, lowest priority first, from always-on → on-demand and from attachments → on-demand, never silently dropped. Each move is recorded in provenance. Priority order: task brief > `PROJECT.md` > profile instructions > `*.instructions.md` (most specific level first) > `MEMORY.md` (newest sections first).
7. **Assemble the bundle:** fill `ContextBundle`, compute `hash` over normalized inputs, and attach provenance.

Requirements:

- **Deterministic:** the same inputs give a byte-identical bundle and hash (golden tests).
- **Cached** by hash: compiling the same target twice in a row costs ≤ 5 ms.
- **Explainable:** `highset context explain` prints every source with included/excluded status, the reason, the section and the estimated tokens.

## 3. Sync targets (CTX-7, HRN-2)

Emitters turn a `ContextBundle` into agent-specific outputs, in one of two delivery modes:

- **Files** (default for project-wide, unrestricted content): written into the worktree, or into the project root for `highset sync`.
- **Launch** (per-session content: task attachments, audience-restricted items, the session token): written to a session-private temp dir outside the repo and passed via flags or env.

### 3.1 Ownership rules (never clobber user content)

- **Markdown files** (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`): HighSet writes only inside its managed block. Everything outside the block is untouched.

  ```markdown
  <!-- highset:begin (generated by HighSet from .highset/; edit the sources, not this block) -->
  …
  <!-- highset:end -->
  ```

  If the file doesn't exist, it is created with only the block. If the block is missing, it is appended at the end.
- **JSON/TOML config files** (`.claude/settings.json`, `.mcp.json`, Codex config, `opencode.json`, `.cursor/mcp.json`): HighSet tracks the keys and entries it owns in `.highset/local/sync-manifest.json`. It adds, updates and removes only those. If the user changed an owned key by hand, HighSet reports a conflict instead of overwriting.
- **Generated directories** (`.claude/agents/`, `.claude/skills/`, `.claude/commands/`, `.cursor/rules/`): HighSet-owned files carry a header marker (`<!-- highset:generated -->` or a frontmatter key `generated_by: highset`). Only files with the marker are updated or removed.
- `highset sync --dry-run` prints a unified diff per file. `highset sync` applies it.
- **Idempotent:** a second run with no input changes produces no diff (tested).
- **No secret values, ever:** MCP server env entries reference env vars that the daemon injects at launch.

### 3.2 Targets in v0.1

| Target id | Writes | Notes |
|---|---|---|
| `agents-md` | `AGENTS.md` managed block | The standard instruction file read by Codex, opencode, Cursor and others. Content: project overview, unrestricted instructions, memory, how to use HighSet MCP tools, the rule "don't edit `.highset/`, use MCP for task state". |
| `claude-code` | `CLAUDE.md` managed block (contains `@AGENTS.md` plus Claude-only content); `.claude/settings.json` (permissions, hooks including the attention bridge); `.claude/agents/*.md` (subagents); `.claude/skills/*/SKILL.md`; `.claude/commands/*.md`; `.mcp.json` | Formats verified in B-007 |
| `codex` | Codex config entries (MCP servers, model, approval/sandbox policy, `notify` hook) through the strategy chosen in A-006 (per-session `CODEX_HOME` overlay or project config) | Must never break the user's own Codex setup or auth |
| `opencode` | `opencode.json` owned entries (MCP, instructions references) | best-effort v0.1 |
| `cursor` | `.cursor/rules/highset-*.mdc` (generated), `.cursor/mcp.json` owned entries | best-effort v0.1 |
| `gemini` | `GEMINI.md` managed block | off by default (`sync.targets`) |

Permission compilation per target is defined in `harness.md` §5.

## 4. Mentions (CTX-10, ADR-0021)

**Grammar** (in any prompt sent through HighSet: the TUI composer, `--prompt`, ACP follow-ups):

```
@file:<path>          file in the worktree (path relative to cwd); a glob expands to multiple files
@kb:<slug>            knowledge item (respecting audience)
@task:T-0042          task brief (title, body, acceptance criteria)
@spec:T-0042          spec/plan/tasks of a task
@pack:<name>          all inline items of a pack
@session:<id>         summary of a past session (+ diff stats)
@url:<https://…>      fetched and converted like kb ingest, not saved unless the user saves it
@<query>              bare: opens the fuzzy picker in the TUI; in the CLI it is an error suggesting candidates
```

- Escape with `\@`. Email addresses and `@` in code spans are not mentions.
- `mention.complete {prefix, kind?}` returns ranked candidates (nucleo) in ≤ 30 ms.
- `mention.resolve {text}` returns the prompt with mentions replaced by short references, plus a list of attachments (content, source, tokens).
- **Size budget per prompt:** 16,000 tokens by default. Oversized items are truncated with an explicit marker (`[truncated: 12,345 more tokens; fetch with highset_knowledge_get id=…]`), never silently.
- For ACP sessions, attachments are sent as resource content blocks if the agent supports them; otherwise they are inlined as fenced sections. For PTY sessions, the composer writes the expanded prompt into the terminal (bracketed paste).

## 5. Explain (CTX-13)

`highset context explain T-0042 --agent codex --profile builder` prints:

- the resolved profile and its origins;
- active packs;
- every candidate item: included (section, tokens) or excluded (reason: audience, level shadowing, budget overflow → on-demand);
- the MCP servers and permissions, as they will be compiled for this agent;
- the output files (or launch artifacts) that would be written.
